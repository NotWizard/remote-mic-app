# 运行日志上限、轮转与权限测试

## 适用版本或分支

- 分支：包含 `Bugs/2026-08-21-runtime-log-unbounded-growth-and-noise.md` 修复的分支
- 平台：macOS 14 及以上（Intel 变体为 macOS 13 及以上）
- 设备：用例 1–4 不需要遥控器；用例 5–7 需要 RC003（长时间连接与语音）

修复前：日志没有任何大小上限，实测常驻 11 天涨到 21.49 MB / 113242 行；文件权限 644，同机其他账户可读；每写一行都要开关一次文件；并且释放虚拟音频的那条消息因为缺少幂等门，单独占了整份日志的 47%。修复后上限为每份 4 MiB、最多保留 3 份归档，文件按 0600 创建并在启动时收紧既有文件权限，另外三类高频消息按整条消息折叠。

## 测试前准备

1. 安装被测版本。
2. 日志目录：`~/Library/Logs/RemoteMic/`，主文件 `runtime.log`，归档为 `runtime.log.1`、`runtime.log.2`、`runtime.log.3`。
3. 记录测试开始时间，以及开始时 `runtime.log` 的大小与行数：`wc -lc ~/Library/Logs/RemoteMic/runtime.log`。
4. 如果本机是从旧版本升级上来的，**先不要删除旧日志**——用例 3 要用它验证权限收紧。

## 用例 1：新建文件的权限必须是 0600

1. 完全退出 App，把日志目录整体移到别处（不要删，留作对照）。
2. 启动 App，等它写入几行。
3. 检查权限：`ls -l ~/Library/Logs/RemoteMic/runtime.log`。
   - 预期：显示 `-rw-------`，即只有当前账户可读写。

失败判定：出现 `-rw-r--r--` 或任何组、其他用户可读的位。

## 用例 2：达到上限时轮转，且总量有界

1. 让 App 持续运行并产生日志（连接遥控器、反复语音、开关按键映射都可以加速）。若需要快速验证，可用测试构建把上限调小；用生产构建则需要积累到 4 MiB。
2. 观察目录。
   - 预期：`runtime.log` 增长到约 4 MiB 后被改名为 `runtime.log.1`，同时新建空的 `runtime.log` 继续写。
   - 预期：继续运行时依次出现 `.2`、`.3`；**不会**出现 `.4`。
   - 预期：目录内日志总量稳定在约 16 MiB（1 份活动 + 3 份归档）以内，不再无上限增长。
3. 检查每个归档的权限。
   - 预期：归档同样只有当前账户可读写。

失败判定：出现第四份归档；总量持续超过约 16 MiB；轮转时丢失正在写入的行；或归档权限被放宽。

## 用例 3：升级路径——既有文件的权限要被收紧

1. 把用例 1 里留下的旧日志目录放回原位，并手动把权限改回宽松：`chmod 644 ~/Library/Logs/RemoteMic/runtime.log`。
2. 启动 App。
3. 再检查权限。
   - 预期：变为 `-rw-------`；旧内容没有被清空。

失败判定：权限仍是 644；或为了收紧权限把用户既有日志删掉了。

## 用例 4：高频消息折叠，但不同内容不得被合并

1. 让遥控器离开范围一段时间，产生连接等待相关的重复行。
2. 检查 `runtime.log`。
   - 预期：`BLE CONNECTING`、`BLE CONNECT TIMEOUT`、`BLE SCANNING` 这三类重复行被折叠，并带有被折叠次数的说明，而不是逐条堆积。
   - 预期：折叠只发生在**整条消息完全相同**时。两条内容不同的行（例如设备名不同、原因字段不同）必须各自成行。
3. 把遥控器带回，间隔较长时间后再离开一次。
   - 预期：时隔较久的重复仍会重新记录，时间线没有被抹掉。

失败判定：内容不同的两行被合并成一条（这会让日志失去定位能力，等于把 A6 的缺陷搬回来）；或折叠后完全看不出发生了多少次。

## 用例 5：单条消息不得再占据日志的大头

1. 正常使用一整个工作日（含多次连接、断连、语音、切换音频设备）。
2. 统计消息分布：把 `runtime.log` 按消息类型归类，看占比最高的那一类。
   - 预期：没有任何单一消息类型占到全部行数的 40% 以上。修复前 `AUDIO RELEASE completed` 一类曾占 47%。

失败判定：任一单类消息重新占到 40% 以上。

## 用例 6：日志仍然足够定位问题

这是本项最容易被做坏的方向——为了瘦身而把有用信息删掉。

1. 故意制造一次"按键没反应"：关闭自定义按键映射后按一下已映射的键。
2. 检查日志。
   - 预期：能读到明确原因（映射未开启），而不是没有任何记录或一句笼统的失败。
3. 故意制造一次语音失败：断开虚拟音频设备后按语音键。
   - 预期：同样能读到具体原因。

失败判定：任一场景在日志里查不到原因。

## 用例 7：稳定功能回归（fork 专有行为，必须逐项确认）

- 语音键触发键可配置：Fn / 右 Command / 右 Option / 右 Shift 四种设置各自仍能触发。
- 外接麦克风采集：关闭"用遥控器自带麦克风收音"后，外接麦路径仍正常。
- 右侧修饰键不粘滞：按住再松开右侧修饰键，不遗留按下状态。
- 自定义快捷键左右侧保真：录入右 Command 组合后，执行时按下的仍是右侧那一枚。

特别确认：轮转发生的那一刻如果正在语音，语音不得中断，也不得丢帧。

失败判定：轮转打断了语音；或任一 fork 行为与上一正式版不一致。

## 日志收集

出现问题时提供：

1. `~/Library/Logs/RemoteMic/` 整个目录（含全部归档）。
2. `ls -l` 输出，用来核对权限。
3. `wc -lc` 在测试开始与结束时的两次输出。
4. 复现时的本地时间、App 版本与 Build。

## 验证边界

- 自动化覆盖：`Tests/RemoteMicTests/RuntimeLogGovernanceTests.swift` 覆盖上限触发轮转、归档数量封顶、新建与既有文件的权限、折叠键必须是整条消息、以及被折叠次数的记录。
- 修复前后的体积对比是**在真实 11 天日志上做的投影**，不是真机长跑实测：113242 → 53823 行（−52.5%）、21.49 → 10.59 MB（−50.7%）、日均 1.92 → 0.95 MB。方法与逐条核对见 `Bugs/2026-08-21-runtime-log-unbounded-growth-and-noise.md`。
- **自动化不覆盖，只能由本手册人工确认**：生产构建下真的写满 4 MiB 后的轮转行为、长时间运行的实际总量、轮转瞬间与语音并发、以及升级路径上的权限收紧。
- 本项修复**没有做过真机长跑验收**。不得据此表述为已验收。
